### Ключевые находки (не наступать на те же грабли)

1. **iOS Safari переставляет оси гироскопа** относительно акселерометра
   (`(devY, devZ, devX)` вместо `(devX, devY, devZ)`). Android — нет. Матрица
   калибровки строится только по гироскопу и **не может** применяться к
   акселерометру напрямую — раньше так и делали, отсюда «геймпад на боку».
   Решение — `gui/sensoralign.go`: физика (`d(gravity)/dt = h·(ω×g)`) между
   двумя моментами покоя определяет перестановку осей и знак `h`.
2. **Клон Madgwick в `gui/ahrs.go`** (комментарии заявляют «точная копия
   PadTest») **не совпадает** с настоящим PadTest по знакам. Реальному PadTest
   нужны перевёрнутые `yaw`, `AccX`, `AccZ` относительно этого клона
   (`dsuYawSign`, `dsuAccSign` в `sensoralign.go`). Проверено вживую в PadTest,
   НЕ по документации/комментариям в коде.
3. **1-Euro фильтр на угловой скорости — вредная идея.** Любой ФНЧ на ω
   добавляет фазовую задержку → клиент интегрирует «хвост» → перелёт при
   резкой остановке. Полностью вырезан (весь `pkg/filter`, настройка в UI,
   переводы).
4. **Дрейф по yaw неизбежен при интеграции гироскопа на 60 Гц** (браузер
   отдаёт не быстрее). За минуту активной игры набегает 8–16°. Решение —
   `gui/attitudeanchor.go`: сервер параллельно ведёт модель «куда доедет
   клиент» и мягко (≤20°/с) подтягивает её к кватерниону
   `DeviceOrientation`, который iOS считает на высокой внутренней частоте.
   **Осторожно с синхронизацией при большой ошибке** — испробовали
   ресинхронизацию при паузе/лаге (чтобы игра "телепортировалась" в верное
   положение, как в MotionSource), результат не заработал стабильно, и
   пользователь решил **откатить эту часть** («не стоит свеч»). Текущий код
   (`a20b33e`) — это последняя версия, которую пользователь подтвердил как
   «околоидеально». НЕ трогать логику `Reset()`/анкера без нового явного
   запроса — там уже была попытка "снапа" после паузы, она не удалась и была
   откачена, история есть в чате, не переизобретать до нового брифинга.
5. **Гравитация и связь осей были глобальными полями**, а не per-profile.
   Калибровка Android перезаписывала `calGravity`, ломая профиль iPhone (знак
   гравитации у платформ разный → геймпад переворачивался). Исправлено в
   `724f82d`: `Profile.CalGravity` и `Profile.SensorFrame` в `gui/app.go`.
   **Если возникнет похожий баг снова — проверить, не читается ли где-то
   глобальное `a.calGravity`/`align.Frame()` в обход профиля.**
6. Хоткей/кнопка «Центрировать» **не делает ничего в игре** — сбрасывает
   только внутренний 3D-вьювер GyroBridge (`a.ahrs.Reset()`). DSU-протокол не
   имеет команды recenter. Убрали автопоказ окна при подключении, поправили
   описания в i18n (`573110e`). Не выдавать это за игровую фичу в будущем.

## Главная будущая задача: USB-режим 2.0 (Arduino)

Пользователь получает **Arduino Nano V3.0 Type-C, ATmega328PB, CH340/FT232**
(гребёнка распаяна). IMU-модуль пока не назван (**спроси явно, если не
сказано** — в прошлый раз вместо названия датчика прилетел путь к файлу).
Будет также контракт/спецификация от привлечённого специалиста ("контракт
чтобы кто угодно с чем угодно мог повторить") — прочитать его первым делом,
как только пользователь пришлёт.

**Оценка готовности алгоритма (уже сообщена пользователю):**
- Калибровка, `sensoralign.go`, автоподстройка bias, deadband/EMA, выход в
  DSU — **платформонезависимы, готовы для сырых данных** хоть с телефона, хоть
  с IMU по USB.
- `attitudeanchor.go` не включится без кватерниона ориентации — это не
  страшно, просто не будет анти-дрейф коррекции, пока прошивка (опционально)
  не начнёт сама считать ориентацию (Madgwick/Mahony на MCU).
- **USB-режим сейчас — только переключатель в UI** (`inputMode` в
  `gui/app.go`), чтения COM-порта ещё нет вообще. Это и есть основная работа.

**Требования к прошивке (уже сформулированы пользователю):**
1. Опрос датчика на высокой частоте (200–1000 Гц), отправка реже.
2. В каждый исходящий пакет — **средняя угловая скорость за интервал**
   (накопленный угол ÷ время), а не последний мгновенный отсчёт — иначе будет
   та же проблема потери вращения, что чинили в `a20b33e` для веб-клиента.
3. Метка времени в **микросекундах** (`micros()`), сервер это уже умеет
   обрабатывать (`TimestampUs` в `MotionFrame`).
4. Опционально: считать ориентацию на MCU и класть в поле кватерниона — тогда
   `attitudeanchor.go` заработает как на iPhone.

**Со стороны ПК нужно написать:** чтение COM-порта (какая библиотека на Go —
не решено, посмотреть `go.mod`/`gui/go.mod`, вероятно `go.bug.st/serial` или
аналог), парсер кадров в `server.MotionFrame`, подключение к тому же
`onFrame`-колбэку, что и WebSocket-путь в `gui/app.go`.

**Установить на чистом ноутбуке (уже сказано пользователю, но проверить факт):**
- Arduino IDE 2.x
- Драйвер CH340 (WCH CH341SER) или FTDI VCP — если Windows не подхватит порт
  сама
- Для ATmega328PB может понадобиться пакет **MiniCore** в Boards Manager —
  проверить по факту, не факт что понадобится
- Для сборки GyroBridge (если сам собирает): Git, Go 1.21+, Node.js 18+,
  `go install github.com/wailsapp/wails/v2/cmd/wails@latest`, WebView2 (в
  Windows 11 обычно уже есть)

## Как проверять любое изменение пайплайна (чек-лист из motion-pipeline.md)

1. Покой плашмя в PadTest: `Accel ≈ (0, −1, 0)`, геймпад ровный.
2. Кивок/крен/поворот совпадают по направлению с телефоном.
3. Удержание наклона 45° (вперёд и вбок) 5 секунд — геймпад не должен
   сползать. Сползание = гироскоп и гравитация не согласованы.
4. Активное кручение → вернуть телефон в исходное положение → геймпад тоже
   должен вернуться. Лаг сети не должен оставлять постоянное смещение.
5. `go test ./gui/...` — `sensoralign_test.go`, `attitudeanchor_test.go`.

Не считать задачу решённой на основании симуляций/юнит-тестов — финальная
проверка всегда через пользователя в PadTest/реальной игре, он тестирует
руками и присылает результат.
